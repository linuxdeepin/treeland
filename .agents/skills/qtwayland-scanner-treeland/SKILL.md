# Treeland QtWayland Scanner

## Scope

Maintain the in-tree `qtwaylandscanner_treeland` generator and the CMake function that invokes it.

Primary files:

- `src/modules/tools/qtwaylandscanner.cpp`: parse Wayland XML and emit Qt-style C++ wrappers
- `src/modules/tools/CMakeLists.txt`: build or import the host scanner and define `local_qtwayland_server_protocol_treeland()`
- `src/modules/*/CMakeLists.txt`: register protocol XML inputs and consume generated files
- build-tree `qwayland-server-*.h/.cpp`: generated server wrappers used for inspection only
- build-tree `wayland-*-server-protocol.h/.c`: C protocol files generated by `wayland-scanner`

Do not edit generated build-tree files as the fix. Change the scanner, XML, or CMake input and regenerate them.

## Route Related Work

Choose the skill by the layer being changed:

- Use this skill for scanner parsing, emitted C++ shape, command-line behavior, generated-file naming, custom commands, and cross-compiling the host tool.
- Use `treeland-private-wayland-protocol` for Treeland-owned XML and server-side module implementation based on `QtWaylandServer::*`.
- Use `upstream-wayland-protocol-wrapper` for upstream protocol wrappers implemented through wlroots/waylib.
- Also use `logging-guidelines` when changing logging emitted by the scanner or logging in its implementation.

Use exactly one protocol-routing skill for protocol integration. It may be combined with this scanner skill only when the task actually changes both generator infrastructure and protocol integration.

## Understand the Generation Pipeline

For `local_qtwayland_server_protocol_treeland(target PROTOCOL ... BASENAME ...)`, preserve this pipeline:

1. Resolve `PROTOCOL` to an absolute XML path.
2. Use the native `wayland-scanner` to produce:
   - `wayland-<BASENAME>-server-protocol.h`
   - `wayland-<BASENAME>-server-protocol.c`
3. Use `qtwaylandscanner_treeland server-header` to produce `qwayland-server-<BASENAME>.h`.
4. Use `qtwaylandscanner_treeland server-code` to produce `qwayland-server-<BASENAME>.cpp`.
5. Add the Qt-style generated `.cpp` to the requested target and make generation complete before that target builds.

The scanner writes generated source to standard output. Keep diagnostics on standard error so shell redirection does not corrupt generated files.

The scanner supports both server and client modes, but the current local CMake helper wires only server generation. Do not imply that client generation is integrated merely because `client-header` and `client-code` exist.

## Preserve Generator Semantics

Before modifying output, inspect all affected branches rather than only the visible declaration:

- XML parsing: protocol, interface, enum, request, event, and argument metadata
- type mapping: `waylandToCType()` and `waylandToQtType()`
- signature generation: `printEvent()` and `printEventHandlerSignature()`
- interface filtering and prefix removal: `ignoreInterface()` and `stripInterfaceName()`
- server header and server code output
- client header and client code output when shared helpers change

Maintain symmetry between declarations and definitions. If a signature changes, update every emitted declaration, static handler, forwarding call, default virtual implementation, and send/request wrapper that uses it.

Treat these cases as compatibility-sensitive:

- `new_id` with and without an `interface`
- destructor requests
- nullable strings and objects
- file descriptors, including closing an fd when dispatch cannot reach a live wrapper
- arrays, whose C and Qt representations differ
- per-resource and global objects
- multiple resources for the same client
- protocol and interface versions
- interface names stripped by an explicit prefix, `qt_`, or `wl_`

Do not casually rename generated classes, methods, namespaces, files, include guards, or includes. Existing modules compile against those names even though the files are generated.

## Command-Line Contract

Preserve the invocation shape:

```text
qtwaylandscanner_treeland MODE SPECFILE [options]
```

Valid modes are `client-header`, `server-header`, `client-code`, and `server-code`.

Supported named options are:

- `--header-path=<path>`
- `--prefix=<prefix>`
- `--add-include=<include>`; repeat it for multiple includes

Legacy positional `header-path` and `prefix` arguments are still consumed by the current CMake helper. When changing argument parsing, verify both the named form and existing positional invocations or migrate every caller in the same change.

Reject unknown modes and options, retain a useful usage message, and return failure for unreadable or malformed XML. Never print partial diagnostics into generated stdout.

## CMake And Cross-Compilation

The scanner is a build-host tool: it must run on the machine performing the build, not on the target architecture.

Preserve all three paths unless intentionally redesigning them:

- native builds compile `qtwaylandscanner_treeland` against Qt Core
- cross-builds may import `QTWAYLANDSCANNER_TREELAND_EXECUTABLE`
- otherwise cross-builds create a native scanner through `ExternalProject`

When editing the helper:

- keep XML and scanner targets in custom-command dependencies
- keep generated files marked `GENERATED`
- keep generated Qt wrappers out of AUTOMOC with `SKIP_AUTOMOC`
- quote paths in CMake commands so source/build paths containing spaces remain valid
- check command failures at configure or build time; do not allow stale generated files to conceal failure
- avoid adding protocol C output twice if the module already lists it through `impl_treeland(SOURCE ...)`

## Workflow

1. Locate the scanner branch and every generated call site affected by the requested change.
2. Inspect one small representative XML containing the relevant request, event, enum, or argument shape.
3. Patch the source generator or CMake helper, never the generated output.
4. Regenerate both header and code for every affected side.
5. Compare declaration/definition signatures and inspect the exact generated region.
6. Compile the scanner and at least one affected generated module.
7. Run broader build/tests when shared type mapping, lifetime behavior, or CMake generation changes.

Keep changes to the copied Qt-style generator focused. Do not perform broad formatting or modernization that obscures output changes.

## Validation

For an existing configured build, prefer targeted checks first:

```bash
cmake --build build --target qtwaylandscanner_treeland
cmake --build build --target generate_protocols_libtreeland_<basename>
cmake --build build --target libtreeland
```

Use the actual configured build directory and generated target name; do not assume `build/` exists. If no build is configured, use the repository presets:

```bash
cmake --preset default
cmake --build --preset default
ctest --test-dir build --output-on-failure
```

For direct scanner checks, generate into temporary files rather than tracked source paths. Exercise header and code together, and exercise both server and client modes when a shared parser or type helper changes.

Review generated output for:

- matching declarations and definitions
- correct C/Qt type conversions
- valid includes and include guards
- correct namespaces and class names
- correct request dispatch and event forwarding
- resource/global destruction behavior
- deterministic output on a second identical run

When changing cross-compilation logic, configure or inspect both the imported-tool and native `ExternalProject` paths even if only a native build can run locally.

## Review Checklist

1. The source of truth, rather than a generated file, is modified.
2. Shared helper changes are checked in all four generation modes.
3. Header and code output remain mutually compatible.
4. Special Wayland argument and lifetime cases remain correct.
5. Diagnostics cannot enter generated stdout.
6. CMake dependencies prevent stale or unordered generation.
7. The scanner remains a native executable during cross-compilation.
8. At least one representative generated module compiles.
9. Protocol business logic follows the appropriate private or upstream protocol skill.
